<summary><strong>❓ Вопрос 1: В чем разница между WHERE и HAVING в агрегатных запросах PostgreSQL на примере файла queries.sql?</strong></summary>

Оператор `WHERE` применяется **до этапа группировки**, то есть он фильтрует исходные строки таблиц еще до того, как начинают вычисляться агрегатные функции. Это означает, что через `WHERE` можно отбирать отдельные записи по обычным полям, например по статусу заказа, идентификатору пользователя, категории товара или диапазону дат.

Оператор `HAVING`, напротив, применяется **после выполнения `GROUP BY`**, то есть уже к сформированным агрегированным группам. Именно поэтому через `HAVING` удобно задавать условия на результаты агрегатных вычислений: сумму, среднее, количество, максимум, минимум и так далее.

В моем файле `queries.sql` это особенно хорошо видно во втором запросе:

```sql
SELECT 
    p.category,
    SUM(oi.quantity) AS total_sold,
    SUM(oi.quantity * oi.unit_price) AS total_revenue
FROM order_items oi
JOIN products p ON oi.product_id = p.product_id
GROUP BY p.category
HAVING SUM(oi.quantity * oi.unit_price) > 10000;
```

Здесь запрос сначала соединяет строки заказов с товарами, затем группирует данные по `p.category`, и только после этого применяет условие:

```sql
HAVING SUM(oi.quantity * oi.unit_price) > 10000;
```

То есть фильтрация идет не по отдельной строке продажи, а по **итоговой выручке всей категории**. Именно поэтому категория `Электроника` остается в результате, а категория `Книги` отсекается.

Если бы я попытался написать это условие через `WHERE`, получилось бы концептуально неверно, потому что на этапе `WHERE` сумма `SUM(oi.quantity * oi.unit_price)` еще не посчитана. Иными словами:

- `WHERE` отвечает на вопрос: какие исходные строки вообще допустить к обработке;
- `HAVING` отвечает на вопрос: какие уже сформированные агрегированные группы оставить в итоговом результате.

На защите удобно сформулировать так: **`WHERE` фильтрует строки до агрегации, `HAVING` фильтрует группы после агрегации**.

<summary><strong>❓ Вопрос 2: Зачем в запросах с GROUP BY нужно перечислять все неагрегированные столбцы, указанные в блоке SELECT?</strong></summary>

Это требование связано с логикой реляционной алгебры и с тем, что после группировки каждая строка результата должна иметь однозначный смысл. Когда мы используем `GROUP BY`, база данных объединяет множество исходных строк в одну агрегированную строку на группу. Поэтому любой столбец, который попадает в `SELECT`, должен быть либо:

1. агрегирован функцией, например `SUM`, `COUNT`, `AVG`, `MIN`, `MAX`;
2. либо включен в список группировки `GROUP BY`.

Если не выполнить это правило, возникнет неопределенность: из какой именно исходной строки брать значение обычного столбца.

Рассмотрим первый запрос из `queries.sql`:

```sql
SELECT 
    o.order_id, u.full_name, o.order_date, o.status,
    SUM(oi.quantity * oi.unit_price) AS total_amount
FROM orders o
JOIN users u ON o.user_id = u.user_id
JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY o.order_id, u.full_name, o.order_date, o.status
ORDER BY total_amount DESC;
```

Здесь `SUM(oi.quantity * oi.unit_price)` — агрегатное выражение, а `o.order_id`, `u.full_name`, `o.order_date`, `o.status` — обычные, неагрегированные столбцы. Значит, все они обязательно должны быть перечислены в `GROUP BY`.

Почему это логично:

- `o.order_id` определяет, по какому заказу строится группа;
- `u.full_name` нужен, чтобы показать владельца заказа;
- `o.order_date` нужен для отображения даты;
- `o.status` нужен для отображения статуса.

Если бы, например, `o.status` не был включен в `GROUP BY`, PostgreSQL не смог бы гарантировать, какое именно значение статуса выводить для агрегированной строки. В сложных запросах это привело бы к неоднозначности и логическим ошибкам.

На защите можно объяснить так: **после группировки каждая строка результата представляет не отдельную запись, а целую группу записей, поэтому все неагрегированные поля должны явно определять эту группу**.

<summary><strong>❓ Вопрос 3: Зачем нужен оператор WITH (CTE) в файле comparison.sql и какая ему существует альтернатива в реляционных СУБД?</strong></summary>

Оператор `WITH` используется для создания **общего табличного выражения** — `CTE` (`Common Table Expression`). Это именованный временный результат подзапроса, который существует только в рамках выполнения одного SQL-оператора.

В файле `comparison.sql` он используется так:

```sql
WITH user_totals AS (
    SELECT 
        u.user_id, u.full_name,
        SUM(oi.quantity * oi.unit_price) AS total_spent
    FROM users u
    JOIN orders o ON u.user_id = o.user_id
    JOIN order_items oi ON o.order_id = oi.order_id
    GROUP BY u.user_id, u.full_name
)
SELECT * FROM user_totals
ORDER BY total_spent DESC
LIMIT 3;
```

Практический смысл здесь следующий:

- сначала отдельным логическим блоком вычисляются суммарные расходы каждого пользователя;
- затем внешний запрос работает уже с готовым промежуточным результатом `user_totals`.

Преимущества такого подхода:

1. **Повышение читаемости.** Запрос разбивается на смысловые этапы.
2. **Удобство сопровождения.** Если понадобится изменить логику расчета сумм, это можно сделать внутри одного именованного блока.
3. **Повторное использование.** В более сложных запросах один и тот же CTE может использоваться дальше в нескольких местах.
4. **Декомпозиция логики.** Сначала вычисление, потом сортировка и ограничение.

Альтернатива CTE в реляционных СУБД — это **вложенный подзапрос**, то есть derived table. Эквивалентная запись выглядела бы так:

```sql
SELECT *
FROM (
    SELECT 
        u.user_id, u.full_name,
        SUM(oi.quantity * oi.unit_price) AS total_spent
    FROM users u
    JOIN orders o ON u.user_id = o.user_id
    JOIN order_items oi ON o.order_id = oi.order_id
    GROUP BY u.user_id, u.full_name
) AS user_totals
ORDER BY total_spent DESC
LIMIT 3;
```

С точки зрения результата оба подхода в данном случае эквивалентны. Но `WITH` выигрывает по читабельности, особенно когда запрос длинный, содержит несколько этапов обработки данных или несколько промежуточных наборов.

На защите можно сказать: **CTE нужен для логической декомпозиции сложного запроса; его основная альтернатива — вложенный подзапрос во `FROM`**.

<summary><strong>❓ Вопрос 4: Что показывает EXPLAIN ANALYZE в файле index_analysis.sql, что такое Seq Scan и Index Scan, почему произошла смена планов и за счет чего индекс ускоряет поиск по order_id?</strong></summary>

`EXPLAIN ANALYZE` — это инструмент PostgreSQL для анализа выполнения запроса. В отличие от простого `EXPLAIN`, который показывает только предполагаемый план, `EXPLAIN ANALYZE` действительно запускает запрос и выводит как выбранную стратегию выполнения, так и фактические показатели времени и обработанных строк.

В файле `index_analysis.sql` исследуется один и тот же запрос:

```sql
SELECT * FROM order_items WHERE order_id = 1;
```

Сначала он анализируется **до создания индекса**, затем создается индекс:

```sql
CREATE INDEX idx_order_items_order_id ON order_items(order_id);
```

После этого запрос анализируется повторно.

### Что такое `Seq Scan`

`Seq Scan` (`Sequential Scan`) — это последовательное сканирование таблицы. База данных читает таблицу строка за строкой и для каждой строки проверяет, выполняется ли условие `order_id = 1`.

Почему это происходило до индекса:

- в таблице не было отдельной поисковой структуры по полю `order_id`;
- следовательно, оптимизатору приходилось просматривать таблицу целиком;
- это стандартная стратегия для неиндексированных условий фильтрации.

Даже если таблица маленькая и время небольшое, сама логика доступа остается полным перебором.

### Что такое `Index Scan`

`Index Scan` — это индексное сканирование. В этом случае PostgreSQL сначала обращается к индексу, который хранит значения индексируемого столбца в специальной упорядоченной структуре, а затем быстро находит строки, соответствующие условию поиска.

Почему это стало возможно после `CREATE INDEX`:

- появился индекс `idx_order_items_order_id` по полю `order_id`;
- оптимизатор оценил, что найти нужные записи через индекс выгоднее, чем просматривать всю таблицу;
- поэтому стратегия доступа к данным изменилась с `Seq Scan` на `Index Scan`.

### Почему произошла смена плана

План выполнения выбирает оптимизатор PostgreSQL. Он оценивает стоимость нескольких возможных стратегий и выбирает наиболее дешевую. После появления индекса у оптимизатора появился новый вариант доступа к данным — через индекс. Так как условие `WHERE order_id = 1` обращается ровно к тому полю, по которому индекс был построен, использование индекса стало естественным и более эффективным вариантом.

### За счет чего индекс ускоряет поиск

Индекс хранит информацию не так, как обычная таблица. Это отдельная структура, предназначенная именно для быстрого поиска по ключу. По смыслу ее можно сравнить с предметным указателем в книге:

- без индекса нужно листать страницы подряд, пока не встретится нужное значение;
- с индексом можно сразу перейти к области, где лежат нужные записи.

То есть индекс сокращает объем чтения:

- не требуется просматривать все строки;
- можно сразу найти только интересующие значения `order_id`;
- уменьшается число операций чтения данных.

### Почему это особенно важно на больших таблицах

В учебном примере таблица маленькая, поэтому зафиксированное время и без индекса, и с индексом очень мало. Но на больших объемах данных разница становится принципиальной:

- `Seq Scan` масштабируется плохо, потому что требует просмотра все большей части таблицы;
- `Index Scan` позволяет быстро находить адресно только нужные записи.

На защите полезно подчеркнуть: **главный результат анализа — не сама величина времени в маленьком примере, а факт смены стратегии доступа с полного перебора на индексный поиск**.

<details>
<summary><strong>❓ Вопрос 5: Что делает оператор $unwind на первой стадии пайплайнов в queries.js и comparison.js, почему без него невозможно выполнить группировку $group по внутренним свойствам товаров, и как работает стадия $lookup с параметрами from, localField, foreignField, as?</strong></summary>

Оператор `$unwind` в MongoDB предназначен для **разворачивания массива**. Если документ содержит массив, то после применения `$unwind` один исходный документ превращается в несколько промежуточных документов — по одному на каждый элемент массива.

Это особенно важно в данной лабораторной работе, потому что в коллекции `orders` состав заказа хранится внутри массива `items`.

Например, документ заказа вида:

```javascript
{
  _id: 1,
  user_id: 1,
  items: [
    { product_id: 1, quantity: 1, price: 75000 },
    { product_id: 2, quantity: 2, price: 1500 }
  ]
}
```

после применения:

```javascript
{ $unwind: "$items" }
```

логически превращается в поток двух отдельных документов, в каждом из которых поле `items` уже содержит только одну товарную позицию.

### Почему без `$unwind` нельзя корректно агрегировать по товарам

Пока `items` остается массивом, MongoDB воспринимает его как единое составное поле. В таком состоянии невозможно корректно:

- суммировать количество по каждой отдельной позиции;
- умножать `quantity` на `price` для каждой строки продажи;
- соединять конкретный `items.product_id` с документом товара;
- группировать продажи по категории товара через `$group`.

Иными словами, `$group` должен работать не с целым массивом, а с потоком атомарных элементов. Именно это и обеспечивает `$unwind`.

### Роль `$unwind` в `queries.js`

В агрегации по категориям:

```javascript
db.orders.aggregate([
    { $unwind: "$items" },
    { $lookup: { from: "products", localField: "items.product_id", foreignField: "_id", as: "product_info" } },
    ...
]);
```

сначала каждая товарная позиция становится отдельным элементом потока, и только потом к ней можно присоединить документ товара из коллекции `products`.

### Роль `$unwind` в `comparison.js`

В расчете ТОП-3 пользователей:

```javascript
{ $unwind: "$items" },
{ $group: { _id: "$user_id", total_spent: { $sum: { $multiply: ["$items.quantity", "$items.price"] } } } }
```

`$unwind` нужен для того, чтобы каждая товарная позиция отдельно участвовала в расчете суммы затрат пользователя. Иначе нельзя было бы корректно просуммировать стоимость всех элементов заказа через `$multiply` и `$sum`.

### Как работает `$lookup`

Стадия `$lookup` — это механизм присоединения данных из другой коллекции. По своей роли она близка к SQL-операции `JOIN`.

Пример из `queries.js`:

```javascript
{ $lookup: { from: "products", localField: "items.product_id", foreignField: "_id", as: "product_info" } }
```

Разбор параметров:

- `from` — коллекция, из которой нужно взять связанные документы. В данном случае это `products`.
- `localField` — поле текущего потока документов, которое содержит значение для сопоставления. Здесь это `items.product_id`.
- `foreignField` — поле в присоединяемой коллекции, по которому идет поиск совпадения. Здесь это `_id` документа товара.
- `as` — имя нового поля, куда MongoDB поместит найденный результат. Здесь это `product_info`.

После `$lookup` результат всегда помещается в массив, даже если найден только один документ. Поэтому в данной работе затем используется дополнительный этап:

```javascript
{ $unwind: "$product_info" }
```

Он превращает массив `product_info` в обычный вложенный объект, чтобы дальше можно было обращаться к полям вроде `product_info.category`.

### Ключевая мысль для защиты

На защите удобно сформулировать это так: **`$unwind` переводит массив вложенных элементов в поток отдельных документов, без чего невозможно агрегировать позиции заказа поштучно; `$lookup` выполняет присоединение данных из другой коллекции по заданным полям и является аналогом `JOIN` в MongoDB**.
