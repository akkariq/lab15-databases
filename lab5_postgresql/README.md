## Архитектура реляционной модели

В реляционной части данные строго нормализованы и разделены на четыре взаимосвязанные таблицы:

1. `users` — хранит пользователей системы.
2. `products` — хранит каталог товаров.
3. `orders` — хранит информацию о заказах и связывает заказ с пользователем.
4. `order_items` — хранит состав каждого заказа, то есть конкретные товарные позиции.

Такое проектирование соответствует классическому реляционному подходу: одна сущность — одна таблица. Это уменьшает дублирование данных, обеспечивает удобство обновления и поддерживает ссылочную целостность.

### Таблица `users`

```sql
CREATE TABLE users (
    user_id SERIAL PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE,
    full_name VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

Построчный разбор:

- `user_id SERIAL PRIMARY KEY` — создается автоинкрементный первичный ключ, который однозначно идентифицирует пользователя.
- `email VARCHAR(255) NOT NULL UNIQUE` — адрес электронной почты обязателен и не может повторяться, что исключает дублирование учетных записей.
- `full_name VARCHAR(255) NOT NULL` — ФИО пользователя обязательно к заполнению.
- `created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP` — если дата создания явно не передана, она автоматически фиксируется текущим временем.

### Таблица `products`

```sql
CREATE TABLE products (
    product_id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    category VARCHAR(100),
    price DECIMAL(10,2) NOT NULL CHECK (price > 0),
    stock_quantity INTEGER DEFAULT 0
);
```

Построчный разбор:

- `product_id SERIAL PRIMARY KEY` — уникальный идентификатор товара.
- `name VARCHAR(255) NOT NULL` — название товара является обязательным полем.
- `category VARCHAR(100)` — категория хранится в текстовом виде.
- `price DECIMAL(10,2) NOT NULL CHECK (price > 0)` — цена обязательна, хранится с точностью до копеек и не может быть нулевой или отрицательной.
- `stock_quantity INTEGER DEFAULT 0` — остаток на складе по умолчанию равен нулю.

### Таблица `orders`

```sql
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(user_id),
    order_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status VARCHAR(50) DEFAULT 'pending'
);
```

Построчный разбор:

- `order_id SERIAL PRIMARY KEY` — уникальный идентификатор заказа.
- `user_id INTEGER REFERENCES users(user_id)` — внешний ключ на таблицу пользователей; заказ неразрывно связан с существующим пользователем.
- `order_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP` — дата заказа автоматически подставляется при вставке записи.
- `status VARCHAR(50) DEFAULT 'pending'` — статус заказа по умолчанию устанавливается как `pending`.

### Таблица `order_items`

```sql
CREATE TABLE order_items (
    order_item_id SERIAL PRIMARY KEY,
    order_id INTEGER REFERENCES orders(order_id),
    product_id INTEGER REFERENCES products(product_id),
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price DECIMAL(10,2) NOT NULL
);
```

Построчный разбор:

- `order_item_id SERIAL PRIMARY KEY` — уникальный идентификатор строки заказа.
- `order_id INTEGER REFERENCES orders(order_id)` — ссылка на заказ, к которому относится строка.
- `product_id INTEGER REFERENCES products(product_id)` — ссылка на товар из каталога.
- `quantity INTEGER NOT NULL CHECK (quantity > 0)` — количество обязательно и должно быть положительным.
- `unit_price DECIMAL(10,2) NOT NULL` — цена фиксируется в самой строке заказа, что правильно с бизнес-точки зрения: даже если цена товара позже изменится, история заказа останется корректной.

### Связи между таблицами

```text
users (1) -------- (M) orders
orders (1) ------- (M) order_items
products (1) ----- (M) order_items
```

Интерпретация связей:

- один пользователь может иметь много заказов;
- один заказ может содержать много строк заказа;
- один товар может встречаться во многих строках заказа.

Именно такая декомпозиция и делает реляционную модель строгой, предсказуемой и удобной для аналитических SQL-запросов.

## Запрос 1. Сумма каждого заказа

```sql
SELECT 
    o.order_id, u.full_name, o.order_date, o.status,
    SUM(oi.quantity * oi.unit_price) AS total_amount
FROM orders o
JOIN users u ON o.user_id = u.user_id
JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY o.order_id, u.full_name, o.order_date, o.status
ORDER BY total_amount DESC;
```

### Логика запроса

- `FROM orders o` — базовой таблицей выбран список заказов.
- `JOIN users u ON o.user_id = u.user_id` — к каждому заказу присоединяется владелец заказа.
- `JOIN order_items oi ON o.order_id = oi.order_id` — к заказу присоединяются все его позиции.
- `SUM(oi.quantity * oi.unit_price)` — для каждой строки заказа вычисляется стоимость позиции, после чего все стоимости суммируются.
- `GROUP BY o.order_id, u.full_name, o.order_date, o.status` — формируются агрегированные группы по каждому отдельному заказу.
- `ORDER BY total_amount DESC` — результаты сортируются по убыванию суммы заказа.

### Результат запроса

| order_id | full_name | status | total_amount |
|---|---|---|---:|
| 1 | Alice Smith | completed | 78000.00 |
| 3 | Charlie Brown | completed | 13000.00 |
| 2 | Bob Johnson | completed | 2500.00 |

### Пояснение вычислений

- Заказ `1`: `1 × 75000 + 2 × 1500 = 78000`.
- Заказ `3`: `2 × 5000 + 1 × 3000 = 13000`.
- Заказ `2`: `1 × 2500 = 2500`.

Скриншот результата выполнения данного запроса сохранен в файле `report/1.png`.

## Запрос 2. Аналитика по категориям

### 3.2 Запрос 2 — аналитический отчёт по категориям

```sql
SELECT 
    p.category,
    SUM(oi.quantity) AS total_sold,
    SUM(oi.quantity * oi.unit_price) AS total_revenue
FROM order_items oi
JOIN products p ON oi.product_id = p.product_id
GROUP BY p.category
HAVING SUM(oi.quantity * oi.unit_price) > 10000;
```

### Логика запроса

- `FROM order_items oi` — анализ начинается со строк заказов, так как именно они содержат факт продажи.
- `JOIN products p ON oi.product_id = p.product_id` — каждая строка заказа связывается с соответствующим товаром и его категорией.
- `GROUP BY p.category` — формируются агрегаты по категориям товаров.
- `SUM(oi.quantity)` — считается количество проданных единиц по категории.
- `SUM(oi.quantity * oi.unit_price)` — считается суммарная выручка по категории.
- `HAVING ... > 10000` — после агрегации отбираются только те категории, чья выручка превысила 10000.

### Результат запроса с фильтром HAVING

| category | total_sold | total_revenue |
|---|---:|---:|
| Электроника | 3 | 78000.00 |

### Полная выручка по базе без фильтра HAVING

| category | total_sold | total_revenue |
|---|---:|---:|
| Электроника | 3 | 78000.00 |
| Книги | 1 | 2500.00 |

### Интерпретация результата

Категория `Электроника` прошла отбор, потому что суммарная выручка составила `78000.00`, что больше порога `10000`. Категория `Книги` не попала в результирующую выборку, потому что ее выручка составила только `2500.00`, а значит была отсечена условием `HAVING`.

Скриншот результата выполнения данного запроса сохранен в файле `report/2.png`.

## Запрос 3. ТОП-3 пользователей через CTE

```sql
WITH user_totals AS (
    SELECT 
        u.user_id, u.full_name,
        SUM(oi.quantity * oi.unit_price) AS total_spent
    FROM users u
    JOIN orders o ON u.user_id = o.user_id
    JOIN order_items oi ON o.order_id = oi.order_id
    GROUP BY u.user_id, u.full_name
)
SELECT * FROM user_totals
ORDER BY total_spent DESC
LIMIT 3;
```

### Почему здесь используется CTE

Оператор `WITH` создает именованное временное выражение `user_totals`, в котором сначала рассчитываются общие суммы трат по каждому пользователю. Затем внешний запрос работает уже с готовым промежуточным набором данных, сортируя его и ограничивая тремя строками.

Такой подход повышает читаемость и делает запрос логически двухэтапным:

1. сначала вычислить итоговые расходы пользователей;
2. затем отобрать из них лидеров.

### Построчный технический разбор

- `WITH user_totals AS (...)` — объявляется общее табличное выражение.
- `SELECT u.user_id, u.full_name, SUM(...) AS total_spent` — формируется набор столбцов: идентификатор пользователя, имя и итоговая сумма расходов.
- `JOIN orders` — к пользователю присоединяются его заказы.
- `JOIN order_items` — к заказам присоединяются строки заказов.
- `SUM(oi.quantity * oi.unit_price)` — по всем строкам заказов пользователя рассчитывается общая сумма расходов.
- `GROUP BY u.user_id, u.full_name` — одна агрегированная строка на каждого пользователя.
- `SELECT * FROM user_totals` — внешний запрос читает уже подготовленный набор.
- `ORDER BY total_spent DESC` — сортирует по убыванию трат.
- `LIMIT 3` — оставляет только трех лидеров.

### Результат запроса

| Место | user_id | full_name | total_spent |
|---|---:|---|---:|
| 1 | 1 | Alice Smith | 78000.00 |
| 2 | 3 | Charlie Brown | 13000.00 |
| 3 | 2 | Bob Johnson | 2500.00 |

Этот результат подтверждает, что наиболее крупным покупателем в реляционной модели является Alice Smith.

## Оптимизация производительности

Файл `index_analysis.sql` посвящен сравнению плана выполнения одного и того же запроса до и после создания индекса.

```sql
EXPLAIN ANALYZE SELECT * FROM order_items WHERE order_id = 1;

CREATE INDEX idx_order_items_order_id ON order_items(order_id);

EXPLAIN ANALYZE SELECT * FROM order_items WHERE order_id = 1;
```

### Что делает первая команда `EXPLAIN ANALYZE`

Команда не просто показывает теоретический план, а действительно выполняет запрос и одновременно измеряет способ доступа к данным, оценочную стоимость плана и фактическое время исполнения. Это важный инструмент диагностики производительности SQL-запросов.

### План до создания индекса

До создания индекса PostgreSQL использовал `SEQ SCAN`, то есть последовательное сканирование таблицы `order_items`.

Это означает следующее:

- СУБД просматривала строки таблицы последовательно.
- Для нахождения строк с `order_id = 1` движок не имел отдельной индексной структуры.
- Даже если таблица маленькая, сам принцип доступа остается полным перебором.

Зафиксированные характеристики:

- тип доступа: `SEQ SCAN`;
- стоимость: `cost 1.1`;
- ожидаемое количество строк: `1 row`;
- фактическое суммарное время: `0.01 ms`.

### Создание индекса

```sql
CREATE INDEX idx_order_items_order_id ON order_items(order_id);
```

Эта команда формирует отдельную индексную структуру по столбцу `order_id`. Теперь СУБД получает возможность сначала найти нужные значения ключа в индексе, а затем перейти непосредственно к соответствующим строкам.

### План после создания индекса

После создания индекса PostgreSQL перешел на `INDEX SCAN`.

Это означает следующее:

- сначала происходит обращение к индексу `idx_order_items_order_id`;
- по ключу `order_id = 1` быстро находятся адреса нужных строк;
- чтение становится адресным, а не сплошным.

Такое переключение плана показывает, что оптимизатор распознал индекс как более выгодный способ доступа к данным по условию фильтрации.

### Почему индекс ускоряет поиск

Индекс по смыслу похож на упорядоченный указатель. Вместо просмотра всей таблицы база данных сначала обращается к компактной структуре поиска, которая позволяет быстро определить, где именно лежат нужные записи. Особенно сильно это проявляется на больших объемах данных, где полный перебор становится дорогим по времени и чтению страниц.

### Практический вывод

В данном учебном примере таблица мала, поэтому абсолютное время выполнения и до, и после индекса очень маленькое. Однако именно смена плана с `SEQ SCAN` на `INDEX SCAN` демонстрирует корректную методологию оптимизации: индекс создается не ради формальности, а для изменения стратегии доступа к данным по часто используемому условию `WHERE order_id = ...`.
